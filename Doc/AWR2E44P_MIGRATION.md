# Radar Program on the AWR2E44PEVM (AWR2X44P), branch `2E44_Standalone_Test`

This branch keeps the AWR2944EVM version of the DSS Radar Program as it was (TDM chain, `mss_main.c` + `RadarSetup.c`, ENET option). Only the settings and the few lines of code that differ between the AWR2944 and the AWR2944P/AWR2E44P (AWR2X44P family) are changed.
The AWR2E44P is the LOP package of the AWR2944P. TI's SDK, SysConfig and CCS call the whole family **AWR2X44P**.

> Status: these changes were prepared against TI's AWR2X44P reference demo (`ti/demo/awr2x44P/mmw_tdm` in mmWave MCU+ SDK 04.07.02.01). They have **not been built or run on hardware yet**. Expect to fix small things on the first build.

---

## 1. One-time setup

1. **Install / check the TI software** (already on the lab PC):
   - CCS 20.4.1 (`C:\ti\ccs2041`)
   - mmWave MCU+ SDK 04.07.02.01 in `C:\ti\mmwave_mcuplus_sdk_04_07_02_01`. It must include `mcu_plus_sdk_awr2x44p_10_02_00_04`.
   - SysConfig 1.28.0 (also in `Dependencies\sysconfig_1.28.0`)
   - Python 3 with `python -m pip install pyserial tqdm xmodem` (needed for flashing, see step 3)
2. **Fill in the missing dependencies.** Close CCS, then run `Dependencies\copy_awr2x44p_dependencies.bat`.
   - The repo copy of `mcu_plus_sdk_awr2x44p_10_02_00_04` is incomplete: there is no `.metadata\product.json`, `source\drivers\lib` is empty, and so on. The AWR2X44P RadarSS firmware is also missing.
   - The script copies the missing files from `C:\ti`. It never deletes anything and is safe to re-run.
3. **Flash the CCS-debug firmware** (once per board, replaces Uniflash; the Uniflash GUI does not support this EVM):
   1. Set SOP to **101** (flash mode). Set the JTAG switch S1 to **XDS**. Use a 12 V supply rated for at least 2.5 A. Power on, press NRST and connect the XDS110 USB.
   2. In Device Manager, note the COM port of *XDS110 Class Application/User UART*.
   3. Run:
      ```bat
      cd C:\ti\mmwave_mcuplus_sdk_04_07_02_01\mmwave_mcuplus_sdk_04_07_02_01\tools\awr2x44P
      python C:\ti\mmwave_mcuplus_sdk_04_07_02_01\mcu_plus_sdk_awr2x44p_10_02_00_04\tools\boot\uart_uniflash.py -p COM<n> --cfg=default.cfg
      ```
      This flashes `sbl_qspi.release.tiimage` and `ti/utils/ccsdebug/awr2x44P_ccsdebug.appimage`. The same files are in `Dependencies\mmwave_mcuplus_sdk_04_07_02_01\tools\awr2x44P` after step 2.
   4. Power off and set SOP to **001** (functional mode).

## 2. Import and build

1. In CCS, remove the old `Radar_Program_mss` / `Radar_Program_dss` from the workspace first. CCS caches the old device and product settings. Then re-open `WorkSpace.theia-workspace` or re-import both project folders.
2. Open each SysConfig file once in the SysConfig editor, check that it loads without errors, and save:
   - `Radar_Program_mss/mss/mss_enet.syscfg` (Debug build of the MSS)
   - `Radar_Program_mss/mss/mss.syscfg` (Release build of the MSS)
   - `Radar_Program_dss/dss/dss.syscfg`

   Each one should show device **AWR2944P**, package **FCCSP (AMX)** (LOP), SDK **MCU_PLUS_SDK_AWR2X44P 10.02.00**.
3. Build **Debug**: first `Radar_Program_dss`, then `Radar_Program_mss`. The MSS post-build step packs the DSS `.rprc` and the RadarSS firmware into `Radar_Program_Debug.appimage`.
   - SysConfig code for **both** cores is generated by each project's pre-build step, which runs SysConfig once with both `.syscfg` files (`mss_enet.syscfg` + `dss.syscfg`). In the Debug configuration, the `.syscfg` files are therefore *excluded from build*, so CCS does not run its own per-file SysConfig step. That step only sees one core. With MCU+ SDK 10.02 it generates broken IPC code, e.g. `gIpcSharedMem[]` → `error #29: expected an expression` in `dssgenerated/ti_drivers_config.c`, and `IPC_SHARED_MEM_SIZE (0U)`. You can still open and edit the `.syscfg` files in the SysConfig editor as usual.
   - If the MSS link step reports missing `System_init`/`Drivers_open`/`Board_init` after a *Clean*, the generated `mssgenerated/*.c` files were not on disk yet when CCS made the file list. Build again (or refresh the project).

## 3. Run from CCS (same flow as before)

1. SOP 001, power on, press NRST, connect USB.
2. Open `targetConfigs/AWR2X44P.ccxml` in either project and select *Start Project-less Debug*.
   - The cores are now **Cortex_R5_0, Cortex_M4_1 and C66xx_DSP**. Cortex_R5_1 no longer exists; leave Cortex_M4_1 alone.
3. Connect **Cortex_R5_0** → *Reset → CPU Reset*. Then do the same for **C66xx_DSP**.
   - TI lists an intermittent C66x connect failure for this device. If it fails, power-cycle and retry.
4. Load `Radar_Program_mss/Debug/Radar_Program_mss.xer5f` on Cortex_R5_0 and `Radar_Program_dss/Debug/Radar_Program_dss.xe66` on C66xx_DSP.
5. Run Cortex_R5_0, then C66xx_DSP. The CLI banner now starts with `AWR2X44P MMW Demo`.

## 4. Configuration (.cfg) changes needed for the new board

The AWR2E44PEVM antenna layout and calibration differ from the AWR2944EVM, so the old `.cfg` files need three changes:

- **`antGeometryCfg`**: copy the line from TI's `profile_3d_3Azim_1ElevTx_awr2E44P.cfg`. After step 1.2 it is in `Dependencies\mmwave_mcuplus_sdk_04_07_02_01\ti\demo\awr2x44P\mmw_tdm\profiles\awr2E44P\`. For the LOP EVM it is:
  `antGeometryCfg 1 0 1 2 1 7 1 9 1 3 1 5 1 10 1 12 1 6 1 8 1 13 1 15 0 9 0 11 0 16 0 18 0.5 0.5`
- **`compRangeBiasAndRxChanPhase`**: the AWR2944EVM values are wrong for this board. Re-measure them with `profile_calibration_awr2E44P.cfg` and a corner reflector, or start from TI's values in the 2E44P profile.
- The simplest first test is TI's `profile_3d_3Azim_1ElevTx_awr2E44P.cfg` unchanged. After that, move your own settings across.

UART output keeps `header.platform = 0x2944`, the same value TI's AWR2X44P demo reports. Host scripts that parse the TLV stream keep working.

## 5. What was changed and why

| File | Change |
|---|---|
| `*/.cproject` | Device `Cortex R.AWR2X44P` / `TMS320C66XX.AWR2X44P`. Product `MCU_PLUS_SDK_AWR2X44P 10.2.0.04`, SysConfig 1.28.0, mmWave SDK 4.7.2.01. `SOC_AWR294X`/`SOC_AWR2944` → `SOC_AWR2X44P` (defining both families would pull in both `sys_common` headers). `MMWAVE_SDK_DEVICE=awr2x44P`. All `*_awr2944` / `*.awr294x.*` libraries → `*_awr2x44P` / `*.awr2x44p.*`. FreeRTOS, ENET and lwIP include paths → `awr2x44p`. The drivers lib now comes from `Dependencies`, not `C:\ti`. |
| `*/.cproject` Debug source entries | `dss/dss.syscfg` and `mss/mss_enet.syscfg` are excluded from the per-file SysConfig build step. The multi-core pre-build step generates both `dssgenerated/` and `mssgenerated/` (see section 2). |
| `*/.cproject` post-build | RadarSS firmware `xwr2x4xp_radarss_metarprc.bin@3`. The DSS image is now core **@1** (on 2X44P: R5F=0, C66=1, M4=2, RSS=3). |
| `*/.project` | `MCU_PLUS_SDK_PATH` → `Dependencies/mcu_plus_sdk_awr2x44p_10_02_00_04`. `lwipopts.h`, `ipc_notify_v1.c` and `enet_apputils.c` now link to the AWR2X44P SDK instead of the AWR294x one. |
| `*/.ccsproject`, `targetConfigs/AWR2X44P.ccxml` | New target configuration for the AWR2X44P (R5F, M4, C66x). The old `AWR2944.ccxml` is left in place but no longer used. |
| `mss/mss_enet.syscfg`, `mss/mss.syscfg`, `dss/dss.syscfg` | Device AWR2944P / FCCSP (AMX) / LOP. The ESM module is removed: it only serviced the AWR294x ECC-aggregator errata. IPC: `r5fss0_1` (does not exist on 2X44P) → `m4ss0_1 = "NONE"`. `mss_enet.syscfg` follows TI's 2X44P demo: `clock` module, NonCached MPU region for the 0xC5000000 mailbox, `edma1.regionId = 0`, `hostportRxCsumOffloadEn = false`. The UART, QSPI and RGMII pins are unchanged; they are the same in TI's LOP demo. The LED stays on PAD_AZ (see section 6). |
| `r5f_linker_BU.cmd`, `c66x_linker.cmd` | The AWR2X44P has 3 MB of L3 (0x88000000–0x882FFFFF). The DSS keeps the first 2.5 MB. The MSS L3 region moved to **0x88280000** (512 KB). **On the AWR2944 build the MSS and DSS L3 regions overlapped at 0x88000000.** The ENET packet/lwIP buffers sat on top of the DSS radar-cube heap, which may explain the ENET problems mentioned in the README. The IPC shared-memory length is now 0x1C80 (ipc_notify uses 32×12 bytes on 2X44P). The lwIP libs named in `.lwip.pools` are now the AWR2X44P builds. Naming a lib there makes the linker pull it in, and the old lines silently linked the AWR294x lwIP from `C:\ti`. |
| `utils/RadarSetup.c` | The ESM/ECC-aggregator errata code is compiled out for `SOC_AWR2X44P`, as in TI's 2X44P demo. `header.platform` and the `tx3PhaseShift` lines (4 TX) are enabled for 2X44P. The SSC setup now auto-detects a 40 or 50 MHz XTAL; the old code assumed 40 MHz, and the AWR2E44PEVM uses 50 MHz. |
| `dss/dss_main.c` | The same ECC/ESM compile-out. `DSS_L3_U_SIZE` stays 2.5 MB for 2X44P. |
| `mss/mmw_cli.c` | CLI banner shows AWR2X44P. |
| `utils/mmwdemo_rfparser.c`, `mmwdemo_flash.c`, `enet_tcpclient.c` | Their `SOC_AWR2X44P` branches included TI's *2X44P demo* `mmw_mss.h`, or a stale local copy. Both have a different `MmwDemo_MSS_MCB` layout from the one the rest of the project uses. They now include the same `ti/demo/awr294x/mmw/mss/mmw_mss.h` as `RadarSetup.c`/`mss_main.c`. Otherwise every access to `gMmwMssMCB` in those files would read the wrong offsets. |
| `Dependencies/copy_awr2x44p_dependencies.bat` | New. See step 1.2. |

Left unchanged on purpose: the macro *name* `MMWAVE_AWR294X_DFP_INSTALL_PATH` (TI's 2X44P projects use the same name). `APP_RESOURCE_FILE` still points at `ti/demo/awr294x/mmw/mmw_resTDM.h`; its values are identical to TI's 2X44P TDM version. The DSS L3 MAR region also stays uncached as before. TI's 2X44P demo enables caching there, but turning it on would change cache-coherency behaviour of the existing DSS code.

## 6. Things to check / known caveats

- **LED demo**: on the AWR2E44PEVM, LED D6 is driven by GPIO_2. `GPIO_LED` uses `PAD_AZ`, which is GPIO_2 on the LOP package. Confirm against the EVM schematic (SWRU631) before relying on it.
- **Release configuration** (`mss.syscfg`, DDM defines) got the same updates but is untested.
- **ENET streaming**: SysConfig and memory are fixed as described above, but this is untested on hardware.
- **Repo size**: the batch file adds roughly the full AWR2X44P MCU+ SDK (libraries and sources) under `Dependencies`. Decide whether to commit it or add it to `.gitignore` and let each user run the script.
- **Install paths**: some sources are still linked straight from `C:\ti\mmwave_mcuplus_sdk_04_07_02_01` (CLI, mmWave control, mmWaveLink). They are device-neutral but require the SDK installed at that path. This was already the case before.
